# 指标原理与设计取舍

改代码前先读这里。很多看似可以简化的地方是踩过坑之后的结果。

## 为什么不用拉普拉斯方差

这是网上最常见的清晰度评分做法，两行代码，但有两个致命问题。

数值随画面内容剧烈变化。杂乱背景的糊片轻松超过干净背景的锐片，因为方差衡量的是高频能量总量，而不是边缘的锐利程度。跨图比较毫无意义。

浅景深会被判废。人像全图方差很低，因为大部分画面是虚化的，而这恰恰是最该保留的片子。

## 边缘宽度

一条被模糊到w像素宽的边，其最大梯度约等于对比度除以w。反过来，局部对比度除以梯度幅值就能反推边缘宽度，单位是像素。分子分母同量纲，对比度被约掉，因此与画面内容基本无关。

实现上，对比度取指定方向上一个窗口内的最大值减最小值，用形态学膨胀腐蚀算；梯度取Sobel在该方向上的投影。

## 三个踩过的坑

### 坑一 沿固定方向扫全图

最初的做法是沿0、45、90、135四个固定方向各扫一遍全图，比较四个读数。

问题是严重的内容耦合。横平竖直的场景在45度方向根本找不到垂直于它的边，只能测到斜着切过的边，宽度天然偏大。后果是所有图的模糊角恒定报45度，各向异性有0.23的虚假本底，抖动判别完全失效。

正确做法是每条边沿它自己的法线方向测量，再按法线朝向分四组比较。各组测的都是各自朝向上最优的宽度，组间差异才真正反映方向性模糊。

### 坑二 用单条参考边做标定

方形像素对斜向边缘的采样天然比水平垂直方向差，这是几何事实不是模糊，必须标定掉。

最初用一条理想直边做参考。标出来的系数在自然图像上仍留有三成残余偏差，因为单条边只能反映一个朝向的情况。

改用西门子星。各朝向等概率出现，是标准分辨率靶。标定后清晰图的各向异性从0.234降到0.041，四组读数几乎相同。

标定的统计量必须和实测一致。最初标定用中位数而实测用低分位数，结果标定值全部撞到测量上限，因为参考图里远离边缘的像素窗口仍覆盖到边，对比度不变但梯度趋零。

### 坑三 全图各向异性

有了可靠的方向性指标后，出现一个新冲突。

浅景深的背景虚化会在全图各向异性上产生假信号，实测能到0.469，与真实抖动的0.52完全重叠。为此加了一条锐度优先规则：只要画面存在足够锐利的区域就判为锐，不看各向异性。

这条规则把抖动全放过了。抖动的片子垂直于运动方向的边缘本来就锐，九像素抖动的峰值宽度只有0.682，和清晰图的0.647没有区别。

真正的区别在于：浅景深是主体区域各方向都锐，只是画面别处虚化；抖动是连最锐的区域也带方向性。所以各向异性必须在最锐区域内部计算。改完之后浅景深从0.469降到0.085，抖动保持0.517和0.604，两者彻底分开。

判定顺序也随之改为方向性优先。

## 曝光

只报告不可逆的问题。高光溢出和暗部死黑的像素信息已经丢失，是删片依据。整体偏亮偏暗不是，RAW有充足的后期空间。

高光溢出按通道判断而非灰度。单通道溢出在高饱和色彩上很常见，比如红花，用灰度判断会漏掉，而那部分色彩细节实际已经丢失。

低反差检测用相对反差，即反差范围除以中位亮度。绝对反差会把欠曝误判成误拍，实测欠曝2.6档的片子绝对反差低于阈值但相对反差正常。镜头盖误拍则是无论怎么归一化都平。

## 连拍分组

感知哈希加拍摄时间双重条件。只用哈希会把同一场景的不同构图错误合并，只用时间会把连续但内容不同的片子归到一起。

哈希用dHash不用aHash。dHash比较相邻像素的大小关系，对整体明暗变化免疫，而连拍中曝光波动很常见。

时间戳优先用EXIF，缺失时回退到文件修改时间。批量导出的JPEG常常丢失EXIF时间，若不回退，分组会退化成纯哈希匹配。实测中这个问题导致14张测试图里13张被并成一组。

只与时间上邻近的十二张比较。连拍必然在时间上相邻，全量两两比较是平方复杂度，两千张就是两百万次。

## 人脸与闭眼

用OpenCV自带的Haar级联，完全离线。代价是只能测正脸，且对眼睛的判断相当粗糙。

因此闭眼只作为提示输出，绝不参与自动判废。检测不到眼睛有三种可能：闭眼、戴墨镜、检测器漏检，三者无法区分。把不确定的信号当成确定的判据，是筛片工具最容易犯也最伤人的错。

真正可靠的是对焦落点检验：把画面最锐的区域和人脸位置对比，人脸在画面里而最锐处在别处，说明对焦跑了。这个判断只依赖人脸框位置，不依赖眼睛检测。

## 性能

RAW读内嵌预览而非完整解码。一张45MP的RAW完整demosaic要两三秒，两千张就是一个多小时；内嵌预览几十毫秒，快两个数量级。预览是机内处理过的JPEG，判断对焦曝光完全够用。

工作分辨率固定长边1400。实测1400与2000的峰值宽度读数差异在0.3%以内，但耗时差三倍。

人脸检测在800像素上做，全分辨率慢三倍且检出率并无提升。

最终约每张0.3秒，两千张十分钟。

## 实测

测试集有十四张合成图，缺陷类型与程度写死在真值文件里。当前自动化验证由`tests/test_photo_cull.py`执行，覆盖报告输出、原图只读、拒绝覆盖和显式XMP写入。

判定结果：

| 类别 | 结果 |
|---|---|
| 清晰片 | 全部判为sharp并保留 |
| 抖动9像素与17像素 | 全部识别为motion_blur |
| 失焦半径8像素 | 识别为defocus并判废 |
| 失焦半径2与4像素 | 判为soft进待定，属保守偏差 |
| 浅景深 | 判为sharp并保留，未被误判为抖动 |
| 过曝 | 高光溢出93.6%，判废 |
| 欠曝2.6档 | 判为sharp并保留，未被误判为误拍 |
| 连拍五张 | 正确识别为一组，选出的最优张与真值一致 |

没有清晰片被误判为废片。两张轻度失焦判为待定而非失焦，是保守方向的偏差，不会造成误删。

## 审计中修掉的问题

这些是功能跑通之后复查发现的，都不属于算法错误，但会在真实批量场景下暴露。

缩略图全量驻留内存。分析阶段给每条记录挂了一张长边1400的缩略图供后续拼印象图用，单张3.9MB，两千张就是7.8GB，必然OOM。改为按需回读：印象图最多展示几十张，回读这几十张不到十秒，内存占用从此与照片数量无关。

输出目录被二次扫描。扫描用的是递归遍历，第二次运行会把上一次生成的废片印象图当成输入，统计数越跑越多，实测14张变15张。现在按目录名排除cull、repaired等输出目录。

清晰度不可测时提前返回，跳过了曝光检查。纯黑的镜头盖误拍、全白的严重过曝都缺乏有效边缘，恰恰是最该判废的一类，却全部落进待定。改为无论清晰度能否测出都继续走曝光判定。

大窗重测没有同步更新宽度图。小窗测量上限是9像素，重度模糊整片撞顶，重测只改了方向读数而分块网格仍用小窗数据，峰值宽度被截断在上限附近，分不出很糊和糊到没法看，连拍组内排序也会失真。现在重测提前到分块统计之前并同步更新。
